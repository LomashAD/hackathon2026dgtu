# ЗАДАЧА ДЛЯ CLAUDE CODE: прототип интеллектуального помощника по внутренним регламентам

Хакатон «Финтех Хаб» (Банк России, Центр документационного обеспечения). Срок: 1,5 дня. Нужен работающий сквозной прототип, а не идеальная архитектура. Сначала сквозной сценарий, потом улучшения. Не добавляй ничего, чего нет в этом плане.

## 1. Цель

Чат-бот, который позволяет сотруднику работать с требованиями Инструкции по документообороту в формате диалога: **быстро находить информацию → понимать её применительно к своей ситуации → переходить к действию** (получить черновик документа по шаблону или узнать, куда обратиться за консультацией).

Важно учесть: решение должно предусматривать **версионность** и возможность обновления/актуализации документов в базе знаний.

## 2. Исходные материалы (все лежат в папке `./data/`)

Все материалы кейса находятся в папке `data/`. Подпапок под типы файлов нет: сам определи по содержимому и названиям, какой файл что собой представляет. В папке должны быть:

- Инструкция по документообороту
- Матрица согласования документов
- Примеры пользовательских запросов
- Шаблоны модульных документов (бланки для заполнения по типовым документам) и рекомендации по работе с модульными документами

Первым делом посмотри содержимое `data/`, определи назначение каждого файла и опиши в `docs/data_notes.md`: список файлов и что в каждом, структуру нумерации пунктов инструкции, формат матрицы, список шаблонов и их поля. Если какого-то из материалов нет в `data/`, остановись и сообщи.

Пути к исходным файлам не зашивай в код: укажи их в `config.yaml`, чтобы файлы можно было заменить.

## 3. Функциональные требования

Основные:
1. **Отвечать на вопросы** по содержанию инструкции.
2. **Находить нужные места:** показывать разделы, пункты и приложения; для каждого найденного фрагмента показывать **процент релевантности**.
3. **Объяснять простым языком.** Не фантазировать: если информации в базе знаний нет, честно сказать об этом (и подсказать, куда обратиться).
4. **Помогать с документами:** подобрать шаблон, сам заполнить его, задавая пользователю уточняющие вопросы, выдать черновик .docx; подсказывать при подготовке документов.

Дополнительные (делать только после того, как работает всё основное):
5. Проверка загруженного черновика документа на соответствие инструкции с рекомендациями по доработке.
6. Расширяемость: новые инструкции/источники подключаются без правки кода.
7. Роли и уровни доступа.

## 4. Ограничения (обязательные)

- Только **open source**, запуск **локально** (Docker Compose, одна команда).
- Отдельный **web-интерфейс** (+ макет поп-ап виджета для встраивания в портал).
- **Защита корпоративных данных при использовании LLM:** только локальные модели, никаких внешних API, никакого исходящего трафика при работе.
- **Предотвращение несанкционированного доступа:** фильтрация по роли/уровню доступа на уровне запроса к индексу, не в ответе.
- **Версионность** документов в базе знаний.
- Возможность расширения функциональности и подключения новых источников.

## 5. Стек

- Python 3.11+, FastAPI (ядро), **Chainlit** (веб-интерфейс чата, источники, загрузка файлов, скачивание .docx)
- **Ollama** + Qwen2.5-7B/14B-Instruct (модель вынести в конфиг; проверить скорость первой)
- Эмбеддинги: **bge-m3** (локально)
- Индекс: **Chroma** (персистентный, локальный) + **rank_bm25** для гибридного поиска
- Парсинг: python-docx, pdfplumber
- Шаблоны: **docxtpl** + YAML-описание полей
- Матрица согласования: CSV/JSON + pandas
- Конфиг через `.env` и `config.yaml`
- Docker Compose: сервисы `app` и `ollama`

## 7. Этапы реализации

После каждого этапа: запусти, проверь, сделай git-коммит. Критерий готовности указан в каждом этапе.

### Этап 1. Скелет и модель
- Структура репозитория, `docker-compose.yml`, Ollama с моделью, пустой Chainlit-чат, который отвечает через LLM.
- **Готово, когда:** `docker compose up` поднимает чат, модель отвечает за приемлемое время. Замерить и записать скорость в README. Если медленно, переключить на квантованную 7B.

### Этап 2. Загрузка и версионность базы знаний
- Парсер инструкции в иерархию «раздел → пункт → подпункт → приложение».
- **Чанкинг по структуре пунктов**, а не по числу символов. Метаданные каждого чанка: `doc_id`, `doc_title`, `version`, `effective_date`, `status` (`active`/`archived`), `section_path` (например `3.2.4`), `appendix`, `heading`, `access_level`, `refs` (номера пунктов, на которые есть отсылки).
- Префикс чанка с заголовком раздела для лучшего поиска.
- `scripts/ingest.py --doc <файл> --version <v> --date <d>`: загружает новую версию, переиндексирует, старую переводит в `archived`. Поиск по умолчанию только по `active`.
- Матрица согласования загружается в таблицу (не в вектора).
- **Готово, когда:** проверено вручную, что нумерация пунктов распознана верно (выборка 10 пунктов сверена с оригиналом); повторный ingest новой версии переводит старую в архив.

### Этап 3. Поиск и ответ
- Пайплайн: учёт истории диалога (переформулировка запроса) → гибридный поиск (вектор + BM25) → объединение → топ-k → подтягивание связанных пунктов по `refs` → оценка релевантности в % → генерация.
- **Процент релевантности** показывать для каждого найденного фрагмента.
- **Порог релевантности** (в `config.yaml`): ниже порога бот отвечает «в базе знаний недостаточно информации» и подсказывает, куда обратиться (подразделение/эксперт из инструкции, если указано).
- Системный промпт ответа: отвечать только по переданным фрагментам; простым языком; структура: краткий ответ → порядок действий по шагам → источники (документ, версия, пункт, приложение); не придумывать пункты и сроки; температура 0–0,2.
- Ответ без ссылок на источники не выдавать.
- **Готово, когда:** на 5 вопросах из файла с примерами запросов в `data/` ответ корректен и содержит верные пункты; на вопросе вне базы бот честно говорит, что информации нет.

### Этап 4. Диалог и уточнения
- Классификатор намерения: вопрос по инструкции / найти раздел / создать документ / проверить документ / «с кем согласовать» / «куда обратиться».
- Если для точного ответа не хватает параметров (тип документа, адресат, срочность, подразделение и т.п.), задавать **один** уточняющий вопрос, а не угадывать.
- Состояние диалога: выбранные параметры и история сохраняются в рамках сессии.
- Вопросы «с кем согласовывать / в какие сроки» отвечаются **из матрицы кодом**, LLM только формулирует текст.
- **Готово, когда:** на неполный запрос бот уточняет, а затем даёт ответ с учётом уточнения.

### Этап 5. Шаблоны документов
- Для каждого шаблона в `templates_yaml/`: id, название, описание (для подбора), список полей (имя, вопрос пользователю, тип, обязательность, валидация, подсказка по инструкции).
- Подбор шаблона по описанию задачи на естественном языке.
- **Slot filling:** бот сам заполняет шаблон, задавая вопросы по очереди, валидирует ответы, заранее подставляет то, что можно вывести (например, согласующие из матрицы).
- Генерация .docx через docxtpl, кнопка скачивания в чате.
- Вместе с черновиком показать краткий чек-лист требований инструкции к этому типу документа со ссылками на пункты.
- **Готово, когда:** от запроса «нужно подготовить документ X» до скачанного заполненного .docx можно дойти в одном диалоге.

### Этап 6. Безопасность и доступ
- Роли (`employee`, `expert`, `admin`) выбираются в UI (в продакшне заменяются на SSO). Фильтр по `access_level` применяется в запросе к индексу.
- Маскирование персональных данных (телефоны, email, ФИО-шаблоны, номера) регулярками перед записью в логи.
- Аудит-лог обращений (кто, когда, запрос, какие источники использованы).
- Защита от prompt injection: текст фрагментов и сообщений пользователя передаётся в промпт как данные в явных разделителях, в системном промпте указано не выполнять инструкции из этих данных.
- Проверить, что в контейнере `app` нет обращений к внешним хостам.
- **Готово, когда:** пользователь с ролью без доступа не получает закрытые фрагменты ни в источниках, ни в ответе.

### Этап 7. Дополнительно (только если Этапы 1–6 готовы)
- **Проверка документа:** загрузка .docx/.pdf → сверка с чек-листом требований инструкции для данного типа документа → отчёт: что соответствует, замечания, пункт инструкции, рекомендация. Достаточно одного-двух типов документов.
- Расширяемость: коллекции источников описываются в `config.yaml`, новые документы подключаются через `ingest.py` без правки кода.
- Обратная связь 👍/👎 и лог вопросов без ответа.

### Этап 8. Качество
- `tests/eval_questions.yaml`: 15–20 вопросов (примеры запросов из `data/` + свои), у каждого ожидаемые пункты; 3–4 вопроса без ответа в базе; 1–2 провокационных (попытка заставить выдумать или обойти доступ).
- `tests/run_eval.py`: считает долю случаев, когда ожидаемый пункт попал в источники, и долю корректных «не знаю».
- Подкрутить размер чанков, веса гибридного поиска, порог и промпты по результатам.

### Этап 9. Артефакты для сдачи (в `docs/`)
- `architecture.md`: архитектура и стек, с mermaid-схемой.
- `scenarios.md`: пользовательские сценарии.
- `kb_interaction.md`: схема взаимодействия с инструкцией и базой знаний (ingest, версии, индекс, поиск).
- `search_and_answering.md`: механизмы поиска и формирования ответов, меры против ошибочных ответов.
- `security.md`: защита данных, разграничение доступа, промышленный контур (SSO, изоляция сети).
- `extensibility.md`: как подключить новые инструкции, шаблоны и процессы.
- `ui_mockup.md` + скриншоты: интерфейс чата и макет поп-ап виджета для портала.
- `demo_script.md`: сценарий демонстрации (раздел 8).
- `README.md`: запуск одной командой, зависимости, требования к железу.

## 8. Сценарий демонстрации (должен работать полностью)

1. Сотрудник формулирует задачу своими словами.
2. Система показывает найденные положения инструкции с процентом релевантности.
3. Формируется ответ простым языком со ссылками на источники.
4. Помощник уточняет недостающую информацию.
5. Пользователь получает нужный шаблон.
6. Система сама заполняет шаблон, задавая уточняющие вопросы, и выдаёт .docx.
7. Вопрос, на который в базе нет ответа: бот честно сообщает об этом.
8. (Доп.) загрузка черновика и отчёт с замечаниями.

## 9. Критерии приёмки (по критериям жюри)

1. **Качество ответов:** есть ссылки на конкретные пункты, нет выдуманных сведений, при отсутствии данных честный отказ.
2. **Сценарии:** понимает запросы на естественном языке, задаёт уточнения, учитывает контекст диалога.
3. **Шаблоны:** подбирает, помогает заполнить, формирует .docx.
4. **Реализуемость:** локальный запуск, защита данных, роли, версии, расширяемость описаны и частично реализованы.
5. **Демо:** весь сценарий из раздела 8 проходит без ручных правок.

## 10. Правила работы

- Сначала сквозной сценарий (этапы 1–5), потом остальное. Не переходи к следующему этапу, пока не выполнен критерий готовности текущего.
- Ничего не выдумывай про содержание инструкции: все факты берутся из `data/`. Если данных не хватает, спрашивай.
- Минимум зависимостей, никаких внешних сервисов и платных API.
- Параметры (модель, пороги, k, размеры чанков, роли) только в `config.yaml`.
- Небольшие коммиты после каждого этапа, в README фиксировать, как запустить и что уже работает.
- Если этап не укладывается по времени, упрощай реализацию, но не убирай обязательные функции (ответы со ссылками, честный отказ, шаблоны, версионность, фильтр доступа).
